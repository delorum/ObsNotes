# Производительность: проверка 0.1.40

Проверены частые пути главного экрана и редактора: свайпы/тапы выбора, поиск, раскрытие разделов, отметка задач, обновление и переход между днями, каталоги назначения, перемещение курсора и внутреннее восстановление. Замеры используют только вымышленные заметки.

## Исправленные повторы

- Выбор раньше вызывал `showDayKeepingPosition`: заново создавались весь экран, структура разделов, Routing.Catalog, DaySearch и Material-элементы. Теперь SelectionControls обновляет рамки и счётчик на существующих View; панель действий меняется только при входе/выходе из режима выбора. Ни чтения хранилища, ни разбора Markdown на пути жеста нет. Поиск, прокрутка и раскрытые записи сохраняются.
- `EditorState.routingCatalog` больше не разбирает документ при каждом обращении. Кеш ограничен одним каталогом формы, переиспользуется копиями частей и инвалидируется по содержимому снимка назначения/шаблона и наличию рабочего файла. Текст, курсор и теги не меняют каталог. Тесты проверяют как повторное использование, так и обновление ключей/разделов/рабочего назначения.
- EditorPanels сравнивает видимые назначения, теги и их строки, связи, корневую роль и оболочки значений. При обычном вводе карточки и метки не пересоздаются; подсветка текста и активной карточки обновляется отдельно. Обработчики получают актуальные формы через supplier, поскольку EditorParts заменяет их при наборе. Снятие обычного раздела обновляет панели на месте; смена оболочки поля/задачи может перестроить редактор с другим заголовком и инструментами.
- Рамки карточек и значок замка при движении курсора обновляются только при изменении состояния. Пустой запрос полей завершается до обхода строк раздела.
- При фоновом обновлении изменившийся дневник разбирается в I/O-очереди; неизменившийся вообще не разбирается. Чтение дневника и рабочего файла, SAF-запись, журнал, nuipogoda, PBKDF2 и операции замка уже выполняются вне UI-потока. Даты и рабочие файлы продолжают читаться по точным путям, без обхода архива. Состояние задачи и изменившийся документ требуют обновления представления; эти обновления сохраняют прежнюю прокрутку.
- Recovery переиспользует системный дескриптор ключа Android Keystore: больше нет повторного открытия KeyStore и поиска alias при каждой правке. Шифр и новый IV создаются для каждой записи; пароль/PIN этим кешем не сохраняются. Сериализация текущего снимка остаётся синхронной для точного восстановления редактора.
- При редактировании нескольких частей исходный текст для переноса тегов разбирается один раз на правку, а не повторно для каждого участника. Шаблон тегов также компилируется один раз.
- Markdown использует заранее скомпилированный шаблон fenced-кода. Для каждого раздела обрабатываются только строки его диапазона, вместо повторного прохода всех строк документа. Не меняются правила выделения блоков, таймстампов и генерируемого кода; отдельный тест проверяет 120 разделов, LF/CRLF, буквальные заголовки внутри кода и точные исходные смещения.

## Замеры

На Samsung Galaxy S23 Ultra, Android 16, `tools/device_group_edit.py` собирает `dumpsys gfxinfo framestats` отдельно после первого и последующих свайпов. В первом прогоне максимальное время завершённых кадров составило 12,1 / 18,3 / 24,3 мс, на итоговом коде — 20,6 / 24,8 / 19,2 мс. В тесте есть предел 150 мс на кадр; это регрессионная граница, а не обещание постоянных 60/120 FPS. Время ожидания UIAutomator не используется как время отклика приложения.

`tools/ParseBenchmark.java` создаёт файл из 120 разделов и 960 блоков (28 650 символов), прогревает JVM и сообщает медиану пяти серий по 60 разборов. На ноутбуке с JDK 21 и `-Xmx256m` версия парсера из 74b1ea8 дала 2,42 мс/разбор, текущая — 0,87 мс/разбор в первом сравнении; повторный запуск дал 1,32 мс/разбор. Выигрыш в этих запусках — примерно 1,8–2,8 раза, с обычной вариативностью микробенчмарка. Это локальный микробенчмарк парсера, а не ускорение всего приложения. Команды для текущей версии находятся в начале исходника; прежнюю можно скомпилировать отдельно из `git show 74b1ea8:core/src/main/java/ru/obsnotes/Markdown.java` и поставить её каталог классов первым в classpath.

Проверка не доказывает отсутствие задержек для заметок любого размера. Поиск меняет набор видимых View при изменении запроса, редактор обновляет разметку при изменении текста, сохранение проверяет исходные версии перед записью. RecyclerView или другой общий механизм виртуализации в рамках этой доработки не вводился.
